## 应如何解释

- async_3 的 p99 中位数下降，但每轮 max 中位数仍接近 1.9ms。每轮只有 96 帧，p99 为排序后第 95 项，少数尖峰的个数变化就会改变 p99。不能把 p99 的倍数当作整体吞吐收益。
- sync A/A 的 p99 比值中位数约 0.998，范围 0.948–1.038；async A/A 约 1.027，范围 0.720–1.079。相同实现也会偏离 1，尤其是异步近尾统计。
- async_4 / async_3 的帧 p99 配对比值中位数约 3.844，范围 0.508–5.318。减少工作者有敏感性变化，但有反向样本；未证明哪次尖峰来自主线程被抢占。还可能受唤醒、缓存、竞争及样本排序影响。
- 4 worker/vector 对 Arena 槽的帧 p99 比值中位数约 1.025，范围 0.740–1.107，和 A/A 噪声重叠，不能声称复用带来稳定提速。启动中位数约从 0.152ms 增到 0.327ms；8 槽的数据预留为 512KiB。保留 vector 默认，Arena 是可切换的生命周期实验。
- async 的需求到安装 p99 约 10.2ms，缺失累计中位数 48；预加载帧 p99 约 0.297ms，但启动约 17.103ms。安装预算与 5ms 帧节奏也构成等待。**异步把代价从帧时间转成资源暂时缺失，预加载把它转到启动时间。**
- 80 次区间 guest 报告 steal 均为 0。只能说虚拟机未报告 stolen tick，不能说主线程没有被调度离开；guest 内部抢占也不会记入 steal。记录 CPU pressure / loadavg 是背景证据，未获取逐线程调度轨迹。

## 对建议的处置

1. A/A 噪声对照：已补 L1 固定输入 baseline A/B 及 L3 sync/async A/B，顺序交替；[L1 数据](../2026-10-15-noise/README.md)。
2. 虚拟机抢占：已记录 Linux steal 原始计数与区间百分比，不改称线程抢占时间。
3. 启动一次触页 vs 首次使用触页：旧 L2 已有两种模式，补齐初始化耗时/缺页和总计；[冷路径数据](../2026-10-15-cold/README.md)。匿名映射/预触页不等于跨平台永久 commit/residency。
4. 3 个工作者：已加入同版本配对；对照合理，因果断言暂不能下。
5. 请求到安装：已增加逐资源需求与受理两种计时，保留缺失累计量，两者互补。
6. L1/L2/L3 串联：已用 L2 Arena 构成 64KiB 独占缓冲槽，由 L1 工作者用于 L3 读取/解码，含异常归还与并发隔离测试；没有硬塞进只支持 128 字节的 Pool。
7. README 一句话：已加入，修正根 README 仍写 L3 尚未实现的旧表格。

不做的部分：不把 3 workers 的变化宣称为抢占因果证据，不把微小缓冲差距当作稳定优化，不用延迟替代并删除缺失累计量，不把原 128 字节 Pool 改成 64KiB 以破坏原实验契约。
