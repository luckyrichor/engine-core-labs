## 文档说明与已确认决策

本文是写给实施 Agent 的产品与技术方案：说明项目要达到什么目标、用什么指标衡量、要做哪些优化、如何验收。具体怎么实现，留给实施时按实际情况决定；本文不含具体代码。

**目标岗位**：游戏引擎开发（通用向、非渲染模块）类岗位，不限于某一家公司。参照腾讯《灰境行者》游戏引擎开发（通用向）岗位的要求，其关键词是物理、性能、资源管线、内存管理、CPU 调度，UE5 为加分项〔事实：来自岗位要求原文〕。

**对象与基线**：仓库 engine-core-labs，方案按提交 c7ca348 的状态编写（附录 A），该提交号〔未验证〕：编写时读到的最新压缩包对应提交 9134c1e，两者关系未核实。开发开始前先核对仓库当前提交与附录 A 是否一致，不一致先更新基线再继续。

**项目要证明的三件事**

- 在真实数据量级和外部基线对照下做过性能工程，而不是只在玩具负载上跑通。
- 每个性能结论都有量化指标、受控实验和可复现的原始结果，负面结果同样如实记录。
- 对调度、内存、资源加载、缓存与并发正确性的原理和取舍有扎实理解，并能解释清楚。

**已确认的决策**

- 范围：岗位 02 的全部关注点；另加物理宽相（S7）、伪共享与线程亲和性（S8）；Chase-Lev 无锁偷取队列并入 S1；加入 UE5 对照。除 UE5 之外的大型引擎不比较。
- 时间：项目所有者表示时间充足，要求把任务做完善；不得因时间原因削减故事、对照或验证。
- 环境：以 tx（虚拟机，4 vCPU，Ubuntu 24.04）为主；可通过 SSH 使用 luowindows（i9-13900HX，24 物理核/32 逻辑线程，Windows 11）做跨平台补测与 UE5 对照；不租用额外机器。
- 权限：允许向 tx 下载公开数据集（总量约 10 GB 以内），允许 sudo 安装 perf 与外部基线库；允许引入一个第三方 FBX 解析库（见附录 C），只用于数据预处理工具，版本固定，许可核对后才能使用。Poly Haven 不使用。
- swap：允许在 tx 正式实验期间临时关闭 swap，但时机由项目所有者决定。实施者必须先告知所有者、等待明确指示，不得自行关闭。
- 检查点：开发按阶段推进，在 F 节标出的三个检查点停下，把结果交给项目所有者，由所有者决定后续安排后再继续。
- 交付：本文为 Docs 文档；面试复述环节放在开发全部结束之后。

**标注约定**：正文中的结论按来源分为三类，写作和后续进度文档都沿用。

- 〔事实〕已在仓库文件、测量原始结果、已打开的官方页面或项目所有者提供的实测报告中核实。
- 〔推断〕由事实推导，尚无实验验证。
- 〔未验证〕来自记忆或仅见搜索结果，必须在第 1 阶段核验后才能使用。

## A 目标与指标定义

总目标：把项目从“在合成负载上跑通的实验”推进到“用真实数据量级、有外部基线、每个数字都能复现、全部 8 条优化故事都能承受面试追问”。不预设任何“预期提升百分比”，所有数字只能来自实际运行的原始结果。

**引擎性能工程通常关注的指标**〔推断：来自常见引擎性能工程实践，不是某家公司的官方指标〕

| 指标 | 为什么关注 | 对应故事 |
| --- | --- | --- |
| 并行吞吐与扩展效率（线程增加时的加速比与并行效率） | 反映多核利用率 | S1、S3、S7 |
| 帧时间稳定性（p99 与卡顿次数，而非平均值） | 玩家感受取决于最慢的帧 | S2、S4、S6 |
| 分配开销与内存占用（分配延迟、峰值驻留、碎片率） | 内存管理是引擎核心职责 | S4、S5 |
| 资源加载延迟与卡顿（请求到可用、缺失帧数、启动耗时） | 资源管线直接决定加载体验 | S5、S6 |
| 调度开销与任务粒度下限 | CPU 调度的有效性边界 | S2、S3 |
| 与业界实现的差距（oneTBB、Taskflow、jemalloc、mimalloc、tcmalloc、UE5） | 说明所做优化处于什么水平 | S1、S3、S4、S7 |
| 多核硬件效应（伪共享、亲和性） | 体现对底层硬件的理解 | S8 |
| 并发正确性（不丢失、不重复、无数据竞争） | 一切性能结论的前提 | 全部 |

**指标口径**（每项在报告中必须按此写法出现）

| 指标 | 定义 | 取数要求 |
| --- | --- | --- |
| 吞吐 | 完成的任务数 ÷ 从开始执行到全部完成的耗时，单位 tasks/s；分 prequeued（不含提交耗时）与 end\_to\_end（含提交耗时） | 沿用仓库现有的暂停/恢复屏障口径 |
| 延迟 p50/p99 | 单个请求从“需要”到“可用”的时间，或单帧耗时；明确写着是批量 p99 还是逐样本 p99 | 样本量需在结果里给出；样本不足 100 的不得报 p99 |
| 重复与汇总 | 独立重复运行次数 ≥ 10（硬下限 5），预热轮不计入；报中位数与 \[min, max\] | 原始每轮数据保存为 CSV |
| 配对比值 | 同一轮内新方案与基线的比值，再取中位数 | 两者交替运行，消除时间漂移 |
| 噪声基线 | A/A：同一方案自己对自己的配对比值范围 | 每条故事在自己的负载上单独测一组 |
| 正确性 | 独立串行校验和、每个任务 ID 恰好执行一次 | 校验失败的运行整个作废，不进入统计 |

**判定规则**

- 配对比值中位数相对基线的变化不超过 10%，或者比值范围与 A/A 噪声范围重叠，结论一律写“无显著提升”，不得写成优化成果。
- 负面结果（变慢、无差异）与正面结果有同等的记录义务，并写明原因假设与是否验证。
- 线程数大于物理核数的结果必须标注“超订”，不得作为扩展性结论。
- 一个数字要能被写进简历或面试回答，必须同时具备：原始结果文件、可重跑脚本、固定的数据与环境指纹。缺一项即标注〔未验证〕。
- 使用 stub（模拟实现）的结果必须在文件名和表头中标明 stub，不与真实运行混用。
- 公开数据集在报告中叫“离线评测数据”或“压测数据”，不写“生产数据”“线上数据”；经过合成放大的要写明放大倍数与方式。

**项目整体验收**

- 8 条优化故事每条都有 E 节规定的九项内容；走不通或结论为“无显著提升”的故事也保留，并如实记录。
- 至少 3 条故事在至少一个真实数据集派生的负载上完成测量。
- 至少有一套与外部基线库的同负载对比结果（调度器或分配器），报告如实写出自己输的项。
- Windows 与 Linux 各有一组完整、口径一致的数据；不足的列入未验证。
- 仓库中的每个公开结论在 docs/status.md 有对应条目，并指向原始结果目录。

| 用途 | Linux 主数据、冷盘实验、软件事件分析 | MSVC 跨平台补测、多核扩展、UE5 对照 |

**硬约束**

- 不同机器的数据不得合并，也不得比较绝对数值（原因：芯片厂商、架构、虚拟化都不同），只比各自机器内的比值。
- **tx 上的 perf 硬件计数器不可用于结论。** 核验报告中 cycles 约 8.8×10^14、branch-misses 占 181%，明显异常。tx 上只用软件事件（task-clock、上下文切换、缺页）与 cpu-clock 采样，IPC、缓存未命中等硬件事件不得出现在任何结论中。
- **swap 规则：** 内存预算、冷路径、资源流送实验不允许发生换页。正式实验前，实施者必须先告知项目所有者并等待明确指示，由所有者决定何时临时关闭 swap；实验结束后告知所有者恢复。每轮记录 swap 使用量的前后值，发生换页的轮次一律作废。
- **页缓存清理：** 冷盘实验前后必须记录缓存大小，证明清理生效，否则该组数据不认。
- **luowindows 的混合核与电源：** 测量时接入电源并使用高性能电源计划（所有者已同意），结束后恢复原计划；线程数不超过性能核线程数的实验绑定到性能核，更多线程的结果一律标注“混合核”，不作为平滑扩展性结论。
- tx 上线程数超过 4 的结果一律标注超订。
- 正式计时期间机器上不运行其他负载；loadavg 不能作为“无后台负载”的证据，以 A/A 噪声为准（tx 是虚拟机，宿主共享带来的噪声同样用 A/A 衡量）。
- 环境指纹（源码 SHA256、编译器版本、CPU 型号、线程数、数据集校验和、swap 状态）写入每组结果的 device.json。
- 原始数据集、下载的库源码、二进制不进仓库；仓库只保存下载脚本、校验和、统计信息与结果。
- 每条故事的结论、取舍与已知局限必须写进 docs/design-decisions.md，供项目所有者事后复述。

**不适用项**：模型调用与预算、API 密钥、鉴权、数据库。登录或账号若在核验数据集时确实需要，由项目所有者在机器上自行完成，凭据不得出现在文档、仓库或对话中。

**UE5 对照的边界与位置**

- UE 任务系统官方文档描述了 Launch、前置依赖、嵌套任务、Pipe 和优先级，但未提到工作窃取。因此对照只比“相同负载下的吞吐与延迟”，不对 UE 内部实现做任何断言。
- 对照只比较任务系统和 FMemory 分配，在独立的最小 UE C++ 工程中进行，不修改 UE 源码。
- 工程目录位置：在 luowindows 上比较 E 盘与 F 盘的剩余空间，选较大者，在其下新建专用目录（建议名为 engine-core-labs-ue5-comparison）。两盘的剩余空间与选择理由记入第 1 阶段报告。
- 仓库中只保存我们自己写的对照代码（experiments/ue5-comparison/），UE 引擎代码、资源与生成的工程文件一律不进仓库。
- 对照必须记录构建配置（Development 或 Shipping、是否编辑器构建）；编辑器构建会带来额外开销〔推断〕，结论应优先基于非编辑器构建。
- UE5 与自己的实现运行在同一台 Windows 机器上，只比较该机器内的比值。

**明确不做**

- 不实现渲染、网络、脚本系统，不写完整物理引擎（只做宽相）。
- 不修改 UE 引擎源码，不重新发布 UE 代码或资源。
- 不把公开数据集写成生产数据；不对外基线库的调优程度做不对等比较（外部库用默认配置，配置记入 device.json）。
- 不提前用“时间不够”削减故事数量；如需削减，由项目所有者决定。

## D 负载与数据设计

本项目没有服务端数据库，这一节的任务是把“真实数据”变成“可重复的压测负载”。原则有三条：任务成本和资源体量尽量来自在真实数据上测到的值，而不是手工取值；任何合成放大都要记录倍数与方式；所有负载都由“数据指纹 + 生成参数 + 随机种子”唯一确定。

| 负载 | 数据来源（详见附录 C） | 规模与合成放大 | 服务的故事 |
| --- | --- | --- | --- |
| 真实任务成本分布 | 在真实网格与文件上实测单任务耗时（如逐三角形包围盒计算、逐文件解析） | 把实测耗时分布重采样到 10^5–10^6 个任务，记录重采样方式与种子 | S1、S2、S3 |
| 包围盒场景 | Bistro：页面给出室内 1,046,609、室内含酒 1,293,691、室外 2,832,120 个三角形；由预处理工具用固定版本的第三方 FBX 解析库提取包围盒，核心库不依赖该库。另用 glTF Sample Assets 中的模型 | 直接用真实三角形或物体的包围盒；规模不足时把场景平移复制到网格上放大 | S7 |
| 分配 trace | 在真实开源程序上自采的分配/释放序列（程序来自 mimalloc-bench 的 real-world 组） | 每条 trace 记录时间戳、大小、线程、分配/释放标识；多线程回放时按线程保留原序 | S4 |
| 资源清单 | glTF Sample Assets 的真实文件大小与格式分布（150 个模型目录，分布在第 1 阶段由 Git tree 计算）；另用 Bistro 压缩包中的纹理等大文件作为更大体量的真实资产（包内容清单已读到 644 项，完整性在第 1 阶段确认〔未验证〕） | 文件数放大到 1000 个以上，总体积超过内存预算 | S5、S6 |
| 伪共享微基准 | 无外部数据，由构造性微基准生成（含专门的最坏伪共享正向对照） | 不适用 | S8 |

**负载规范**（每个负载在仓库中都有一份描述文件，字段固定）

- 负载名、数据集名与版本、原始文件校验和、过滤规则、生成参数、随机种子、规模（任务数/对象数/字节数）、合成放大倍数与方式。
- 负载生成器对同一指纹必须产生字节级相同的输出，并在测试中验证。
- 每个负载同时提供一个独立、不依赖被测实现的答案（如串行校验和、暴力配对计数），用来防止“自己评自己”的循环评测。

**与仓库的关系**：原始数据与下载的压缩包一律放在仓库外的数据目录，并在 .gitignore 中排除；仓库只保存下载脚本、校验和、统计信息（文件数、大小分布、三角形数、耗时分布摘要）。下载脚本必须校验校验和，校验不符即停止，不得静默继续。

## E 优化故事

共 8 条，深度优先于广度。每条都必须完整包含九项：问题、朴素基线、定位方法、假设、改动、对照实验、指标、代价、反向验证。假设只是待验证的猜想，不是结论；结论只能在实验后写，且按 A 节的判定规则表述。所有对照实验均按 A 节规定重复、配对、比 A/A。

### S1 偷任务的收益取决于任务成本分布

- **问题**：仓库现有“偏斜负载约 3.6 倍”来自与任务 ID 取模绑定的周期夹具（重任务全落在队列 0），随机布局下同一指标只有约 1.14 倍；真实成本分布下的收益未知。
- **朴素基线**：按 ID 静态分发、不偷取（仓库已有）。
- **定位方法**：用真实耗时分布计算“最大队列负载 ÷ 平均队列负载”作为收益上限〔推断〕，再用偷取次数与空闲时间占比验证。
- **假设**：实测收益接近该上限，并随任务变小被偷取开销侵蚀。
- **改动**：新增“一次偷一半”策略与 Chase-Lev 无锁双端队列（与现有互斥锁队列对比）；Chase-Lev 须通过 TSan 与“每个 ID 恰好执行一次”检查，内存序取舍逐项说明理由。接入 oneTBB、Taskflow、std::async 作外部参照。
- **对照实验**：真实成本分布 × 线程数 × {不偷、偷一个、偷一半、Chase-Lev、外部库}；tx 上 8 线程标超订；luowindows 按物理核扩展并区分性能核与能效核。
- **指标**：吞吐（prequeued 与 end\_to\_end）、空闲时间占比、偷取成功率。
- **代价**：锁竞争、实现复杂度、小任务下可能反而变慢；无锁队列内存序难以证明。
- **反向验证**：成本均匀时偷取不应有收益并量化其开销；关闭偷取应复现基线。

### S2 提交与唤醒路径的开销

- **问题**：提交路径内部（锁、入队、唤醒）各占多少从未定位；仓库的 perf 证据只在旧执行器上。
- **朴素基线**：当前执行器（共享生命周期锁、原子计数、每 worker 独立唤醒）。
- **定位方法**：tx 上用 perf 软件事件与 cpu-clock 采样，统计 futex 调用与上下文切换（不用硬件计数器），再在代码里分阶段计时交叉验证。
- **假设**（候选，由定位结果决定改哪个）：开销主要来自共享锁竞争，或来自每次提交都触发的唤醒系统调用。
- **改动**：一次只改定位出的主因——批量提交，或仅在目标 worker 确在睡眠时才唤醒；不同时改两个。
- **对照实验**：新旧执行器同负载交替运行，提交线程数 1/2/4，分 prequeued 与 end\_to\_end。
- **指标**：提交耗时 p50/p99（逐批）、end\_to\_end 吞吐、futex 调用次数。
- **代价**：批量抬高首个任务的延迟；唤醒条件复杂化带来丢唤醒风险。
- **反向验证**：开关回退应复现旧数据；TSan 与“每个 ID 恰好执行一次”通过，压力测试中无丢唤醒导致的挂起。

### S3 任务粒度与调度开销的拐点

- **问题**：不知道单任务工作量小到什么程度时，调度开销会抵消并行收益。
- **朴素基线**：同一总工作量的串行执行，以及每个元素一个任务的最细粒度并行。
- **定位方法**：在约 100 ns 到 1 ms 的单任务工作量范围内扫描，绘制“加速比对粒度”曲线，找到并行不再比串行快的临界粒度。
- **假设**：存在临界粒度，低于它并行反而更慢；把多个小任务合成一个块可以越过拐点，代价是负载更不均匀。
- **改动**：在调度核心之上提供分块的并行遍历接口（块大小可固定或自适应），不改核心。
- **对照实验**：粒度 × 块大小 × 线程数；对比 oneTBB、Taskflow，以及 luowindows 上 UE 的并行遍历。
- **指标**：加速比、调度开销占总耗时比例、负载不均程度。
- **代价**：块太大会引入长尾和空闲，与 S1 的收益相互抑制。
- **反向验证**：块大小取 1 时应回到未分块的结果；单任务工作量足够大时分块不应有收益。

### S4 线程缓存 + size class 分配器

- **问题**：现有分配器都是专用型，没有多线程通用分配方案，无法回答“真实 malloc 为什么快”。
- **朴素基线**：单全局锁的堆（仓库已有）与系统 glibc malloc。
- **定位方法**：用真实程序的分配 trace 回放，统计大小分布（依据其设计 size class），并看多线程回放时的锁等待占比。
- **假设**：线程本地缓存使热路径无锁，多线程吞吐随线程数改善；代价是缓存中滞留的空闲内存。
- **改动**：实现 size class 分配器，带线程缓存（批量补货/归还、每类数量与总字节上限）、中央空闲链表、大块直接向系统申请。
- **对照实验**：至少 3 条真实 trace × 线程数 1/2/4 × {全局锁版、自实现、glibc、jemalloc、mimalloc、tcmalloc}，同时记录峰值驻留内存。
- **指标**：回放吞吐、单次分配延迟 p99（按批计时）、峰值 RSS、碎片率。
- **代价**：滞留内存、实现复杂度。
- **反向验证**：缓存上限设为 0 应退化为全局锁版；调小上限观察滞留量与吞吐的折中。

### S5 冷路径：页错误与预触页

- **问题**：仓库已测出首次触碰内存比预触页慢两个数量级，但只在 Linux 4KiB 页上测过，没有大页、Windows 与内存建议接口的对照。
- **朴素基线**：按需分配、首次触碰时才缺页。
- **定位方法**：统计次要缺页次数（Linux 用 getrusage 或 perf 的 page-faults 软件事件；Windows 的等价方法〔未验证〕，第 1 阶段确定）。
- **假设**：预触页把缺页成本从运行期移到启动期；大页减少缺页次数，代价是内存浪费与可用性限制。
- **改动**：Arena 与 Pool 增加“预触页”开关与“大页”选项（tx 上透明大页为 madvise 模式，需在代码中显式申请〔事实〕；Windows 大页需要特权〔未验证〕）。
- **对照实验**：块大小 × 预触页开/关 × 大页开/关，每组在全新进程中重复。
- **指标**：首触延迟分布、启动耗时、常驻 RSS。
- **代价**：启动变慢、内存常驻。
- **反向验证**：预触页后常驻 RSS 应等于预留量；关闭开关应恢复原数据。

### S6 资源流送：真实资产、冷盘与内存预算

- **问题**：L3 目前只有 32 个 64KiB 的热缓存文件，没有冷盘 I/O、内存上限、淘汰和资源依赖。
- **朴素基线**：仓库现有的同步/异步/预加载三种策略，运行在真实资产清单上。
- **定位方法**：分解“请求到可用”延迟（排队、I/O、解码、提交）；冷盘用 sudo 清理页缓存后测量（记录清理前后的缓存大小），并用 fio 测出磁盘带宽作为上限参照。
- **假设**：资源总量超过内存预算后预加载不可行；异步的“缺失帧数”由每帧提交上限和在飞上限结构性决定（仓库已有推导，尚未用真实资产验证）；访问局部性高时 LRU 淘汰命中率高。
- **改动**：增加内存预算与 LRU 淘汰、依赖句柄（模型先于其纹理完成）、按需求优先级排序。
- **对照实验**：访问序列（顺序、随机、高局部性）× 预算（总量的 20%、50%、100%）× 策略；内存预算实验须遵守 B 节的 swap 规则。
- **指标**：请求到可用延迟 p50/p99、命中率、缺失帧数、峰值内存、磁盘读字节数。
- **代价**：实现复杂度、淘汰造成的重复加载。
- **反向验证**：预算等于 100% 时，淘汰版应与无淘汰版结果一致；失败的加载不得被安装。

### S7 物理宽相

- **问题**：岗位要求涉及物理，仓库目前没有任何物理相关实验。
- **朴素基线**：O(n²) 暴力配对，同时作为正确性的独立答案。
- **定位方法**：统计配对数与耗时随物体数的增长曲线，用 perf 看遍历开销。
- **假设**：均匀密度下均匀网格最优，密度不均（如 Bistro 室内）时 BVH 或扫描剪枝更优〔推断〕；并行遍历只在配对测试量超过 S3 拐点时才有收益。
- **改动**：实现均匀网格、扫描剪枝、BVH 三种宽相，接口相同；查询阶段通过 L1 并行。
- **对照实验**：场景（Bistro AABB——由预处理工具用固定版本的第三方 FBX 解析库提取三角形包围盒，核心库不依赖该库；均匀随机；聚簇）× 规模（约 10^3 到 10^6）× 结构。Box2D 是 2D 引擎，只用于 2D 场景对照；若无法把其宽相阶段单独计时，则不与它比较并列为未验证，不得用整步耗时代替。
- **指标**：配对结果与暴力版一致、构建时间、查询时间、物体移动后的更新时间、内存占用。
- **代价**：更新与重建开销、实现复杂度。
- **反向验证**：规模很小时暴力版应最快，报告各结构的交叉点。

### S8 伪共享、缓存行与线程亲和性

- **问题**：每个 worker 的队列元数据、原子计数器、统计字段如果落在同一缓存行，会产生伪共享。仓库没有检查过缓存行布局，也没有线程亲和性实验。
- **朴素基线**：当前布局，不做对齐，不绑核。
- **定位方法**：tx 上硬件计数器不可用，因此采用受控对照定位：逐个给计数器、队列头尾、统计块加缓存行填充，观察吞吐差异；luowindows 上用 Visual Studio 性能分析器采样查看热点。结论不依赖硬件事件计数。
- **假设**：多个 worker 频繁写入的相邻字段会互相拖慢，影响随线程数增大而增大；绑核可以减少迁移，但在虚拟机与混合核上的收益取决于调度器。
- **改动**：一次只对一个结构加缓存行对齐或填充；增加线程绑核开关（Linux 使用 sched\_setaffinity，Windows 使用亲和性掩码，并区分性能核与能效核〔未验证〕）。
- **对照实验**：填充开/关 × 逐个结构 × 线程数 × 绑核开/关，tx 与 luowindows 分别进行。必须包含一个专门构造的“最坏伪共享”微基准作为正向对照，证明这套方法确实能测出差异。
- **指标**：吞吐中位数与范围；tx 上再加 cpu-migrations 软件事件次数。
- **代价**：填充造成内存膨胀；缓存行大小在两台机器上均需实测确认〔推断：x86 通常为 64 字节〕。
- **反向验证**：在微基准中去掉伪共享应恢复吞吐；单线程时填充不应有收益；对没有竞争的结构加填充也不应有收益，结果如实记录。

## 附录 B 实验接口与测量协议约定

本项目没有服务接口，这里统一的是“实验程序与输入输出”的约定，使任何一组结果都能被脚本自动汇总与复现。

- **统一命令行参数**：每个实验程序都接受负载名、负载指纹、线程数、重复次数、预热次数、随机种子、输出目录；实现选择（自己的版本或某个外部库）通过适配层的名字指定。
- **适配层接口**：外部库与自己的实现对外暴露相同的“提交任务 / 等待完成 / 分配 / 释放 / 请求资源”等操作，适配层不得修改被测实现的行为。
- **结果目录**：docs/measurements/<日期>-<故事编号>-<机器>/，内容固定为每轮原始数据 raw.csv、汇总 summary.csv、环境与指纹 device.json、复现命令说明、A/A 噪声组。
- **raw.csv 列**：轮次、实现名、负载名、线程数、口径（prequeued/end\_to\_end）、指标值、单位、校验是否通过、是否 stub、本轮前后的 swap 使用量、是否绑核及绑定的逻辑线程编号。
- **device.json 字段**：机器名、系统、CPU 型号与核数、内存、编译器与版本、编译选项、源码 SHA256、数据集校验和、外部库版本与配置（tcmalloc 必须写明是 gperftools 还是 google/tcmalloc）、是否超订、swap 状态、电源计划（Windows）、透明大页设置（Linux）、性能核与能效核的线程编号（Windows）。
- **汇总脚本**：只从 raw.csv 计算中位数、范围、配对比值与“无显著提升”判定；判定规则只在一个地方定义，所有故事共用。
- **失败处理**：校验失败或发生换页的运行标记为无效并单独列出，不进入汇总。
